# blog.snail ― 技術メモを編集者レビュー付きでブログ記事化する

`~/memo` や `~/PROJECTS` の素材から、カタツムリワークスの blog 記事の下書きを作るパイプラインです。書いた本人（この Claude）だけで完結させず、**別の LLM エージェント3者に「雑誌・書籍の編集者」として査読させてから仕上げる**のが肝です。

## 対象・前提

- 出力先ブログ: `~/PROJECTS/katatsumuri-work/blog`（Hugo。親 repo の submodule）
- 記事の置き場: `blog/content/posts/YYYY-MM-DD-{slug}.md`
- パーマリンク: `/:year/:month/:day/:slug/`。**未来日の記事は Hugo 既定で当日まで非表示**（＝日付を振れば連日公開に使える）
- 規約は親 repo の `AGENTS.md`（言語＝日本語、トーン、ブランチ戦略、コミット前チェック）に従う
- **公開は自動**。blog repo の `.github/workflows/deploy.yml` が main への push と日次（JST 09:05）で Firebase Hosting へデプロイする。マージすれば手動デプロイは不要で、未来日の記事も当日の日次ビルドで自動的に出る

作業前に必ず、既存記事を1〜2本読んでトーンを合わせること（`blog/content/posts/` の直近記事）。

## パイプライン

### 0. 入力を確定する
ユーザーの指定（日付／memo パス／repo／ネタ memo）を受け取る。**曖昧なら `AskUserQuestion` で確認**してから進む（何を元ネタにするか、公開日、`draft` の扱い＝先積みか下書きか）。1回の実行で1記事を基本とする。

### 1. 素材を読む
指定された daily_report・技術メモ・実装コードを読む。ここの目的は**「人柱ポイント（ハマった点）」を掴む**こと。記事の核をどこに置くかは次の手順で決める。

### 2. 想定読者と読後感を決める（`core-message-writing`）
書き始める前に `core-message-writing` skill を呼び、**想定読者**（誰が読むか・その人が
すでに知っていることは何か）と**読後感**（どう感じてほしいか・何をしてほしいか）を
言語化する。判断軸の中身はあちらが単一の出所なので、ここには写さない。

**ここに置く理由。** 素材を見ないと想定読者も読後感も決められないので手順1 より前には
置けない。逆に書き出し（手順6）より後ろだと、**何を削るかの判断根拠として使えない**ので
遅い。素材を読んだ直後のここが唯一の置き場所になる。

**この工程が埋める穴。** 3者の編集者レビューは事実誤りをよく拾う（09-22 の記事は
4周して計 8 件）が、**「一番言いたいことが埋もれている」は誰も指摘しなかった**。
レビュー周回のコストが実測で重いので、上流で締める。

決めた想定読者・読後感は**レビュープロンプトの `{{CORE_MESSAGE}}` に渡す**（手順8）。
宣言した狙いに照らして記事がどうかを 3者に見てもらうため。渡さないと、レビュアーは
狙いを推測しながら構成を評価することになる。

**あの skill は2段構成なので、ここで終わりではない。** 「① 書く前に決める」がこの手順、
「② 書いた後に、コアを際立たせる方向へ調整する」と最終チェックリストは**手順6 の直後**に
当てる（手順7 の `humanizer` より前）。**中身と構成を直してから表層の言い回しを直す**順に
しないと、humanizer で整えた文を後から削ることになる。

### 3. ぼかす（機密の除去・抽象化）
公開物に載せてはいけない情報を除去・抽象化する。**ここは必須工程**。
- 顧客名・取引先名 → 「あるクライアント」等に抽象化、またはプレースホルダ
- 個人名・自宅/個人の絶対パス（`/Users/...`、OneDrive の実パス等）→ プレースホルダ
- 生の認証情報・トークン・内部 URL・センシティブな数値 → 除去
- 判断に迷う値は載せない側に倒す。元ネタに顧客名リスト等があれば突き合わせて漏れを確認する。

**書いたら機械のチェックを走らせる。** 手順としての指示だけだと、そのときの注意力に
依存する。blog repo にスクリプトがある。

```sh
cd ~/PROJECTS/katatsumuri-work/blog
gcloud secrets versions access latest --secret=blog-sensitive-terms \
  --project=katatsumuri-work > /tmp/terms.txt
python3 scripts/check_sensitive.py --terms-file /tmp/terms.txt
rm -f /tmp/terms.txt
```

- **落とすもの**: 認証情報・個人の絶対パス・内部 IP・機微な固有名詞（顧客名・個人名・地名）
- **確認だけ**: 金額・住所らしき語（文脈で可否が変わるので落とさない）
- **目視用**: 外部 URL の全件。内部 URL が混ざっていないか見る

顧客名などの機微な固有名詞は **blog repo が public なので置けない**。Secret Manager の
`blog-sensitive-terms` にある。**リストを渡さないと顧客名の検査だけ行われない**ので、
上のように取り出して渡すこと（渡さない場合は警告が出るが、他の検査は走る）。

**main 宛ての PR では Cloud Build が同じチェックを自動で走らせ、落ちると merge できない**
（トリガー `blog-pr-sensitive-check`）。手元で先に通しておけば PR で驚かない。

誤検出だと判断したものは `blog/scripts/sensitive-allow.txt` に積む。ただし
**機微な語そのものをここに書いてはいけない**（public repo なので、検知したい語を
自分で公開することになる）。許可リストは `${SYNC_PAT}` のような、機微でない誤検出のためのもの。

機微な語が正当な理由で記事に必要なときは、**記事側を直すか、用語リストから外すかを
ユーザーに確認する**。2026-09-24 に実際に踏んだ判断で、結論は「GitHub のユーザー名は
公開情報なのでリストから外す」だった。

### 4. 整文（媒体トーンに整える）
既存記事に合わせる。
- 「〜です／〜ます」基調、柔らかい表現（「〜しそうです」「〜かなと思います」）を混ぜる。カタツムリらしくゆっくり
- `## 見出し` で構成し、コードは言語付きフェンスで示す
- 主張の根拠になる箇所は**公式ドキュメントの URL** を「参考:」として添える（一次情報優先）
- 最後に「## まとめ」で持ち帰りを整理する

### 5. frontmatter を生成
```yaml
---
title: '…'
slug: '…'                 # 英小文字・ハイフン
date: YYYY-MM-DDT09:00:00+09:00   # 時刻+TZ 必須。tech は 09:00 が既定
categories: ['tech']      # tech | zatsudan | yomoyamo
tags: ['…']               # 小文字スラッグ。言語/FW/ツール名
draft: false              # 先積み運用なら false + 未来日。純粋な下書きなら true
---
```

### 6. 記事を書き出す
`blog/content/posts/YYYY-MM-DD-{slug}.md` に保存する。

書き出したら `core-message-writing` の「② 書いた後に、コアを際立たせる方向へ調整する」と
**最終チェックリスト**を当てる（手順2 で決めた読後感に照らす）。とくに**見出しだけを上から
読んでストーリーが伝わるか**は、この媒体の記事で崩れやすい。

### 7. `humanizer` を通す（AI っぽさを落とす）

**編集者レビューの前**に、初稿へ `humanizer` skill を当てる。personal スコープに入っている
（`~/.claude/skills/humanizer`。実体は private-dotfiles）。

**なぜレビューの前か。** 太字の過密・「実は」・「結論を先に言うと」といった癖は、
**毎周レビューで指摘されていた**ものだった。上流で落としておけば、レビューを事実検証に
集中させられる。

**2026-10-10 に日本語で判定済み。** 26 パターンのうち 6〜7 が発火し、残りは英語固有で
空振りする（害はない）。

| 発火するもの | 空振りするもの |
|---|---|
| 太字の装飾（**最多**）／一行の締め・劇的な短文／前置き（「結論を先に言うと」「正直に言うと」）／格言調／「実は」／Not X but Y | ダッシュ／ハイフン複合語／受動態（日本語は主語省略が常態なので基準にならない）／is-has 回避／カーリー引用符／英単語リスト |

**コードブロック・コマンド出力・英語原文・コミットメッセージ・数値には手を入れない。**
これは実測で確認している。

#### 太字はこのブログの基準に寄せる

**humanizer は「装飾の太字は全部外す」方針だが、そこまでやらない。**
既存 21 記事の実測（コードフェンス除外）では、**書き進むうちに密度が上がっていた**。

| | 密度（箇所 / 1000 字） |
|---|---|
| 2026-06 の記事 3 本 | **4.2 / 4.4 / 4.6** |
| 中央値（21 本） | 7.1 |
| 2026-09-29 snail-cli | 9.5 |
| 2026-09-17 ai-driven-company-ops | 12.7 |

**初期の 4〜5 をこのブログの本来の密度と見て、そこを目標にする。** 全部外すと流し読みで
要点が拾えなくなる。

#### 通したあとに必ず確認する

**humanizer は表現の後退を生むことがある。** 実測で 3 件あった。

- 意図の言い直しが消えた
- 「絶対に」が落ちた
- **元の文に無い条件を補った**（1 箇所）

**新しい事実の捏造は無かったが、最後のものは踏み込んでいる。**
だから humanizer のあとに編集者レビューを置く順序になっている。
**通して終わりにせず、変更箇所を before / after で見る。**

#### 既存記事には通さない

公開済みを書き換えると再デプロイが走り、履歴も汚れる。**今後書く記事から適用する。**

### 8. 編集者チームレビュー（`editorial-review`）
**検証（手順9）の前に** `editorial-review` skill を呼び、書いた本人以外の LLM に
雑誌・書籍の編集者として査読させる。**回し方はあちらが単一の出所**で、blog から渡すものは
下の「編集者チームレビューの回し方」にまとめてある。
- 指摘を集約し、**批判的に取捨選択**して記事に反映する（全指摘を鵜呑みにしない。レビュアーが的外れなこともある）
- **1周で終わらせない。** 止めどきの判定は `editorial-review` の「反映したら通し読みして、もう一周投げる」に従う
- 反映した指摘／見送った指摘とその理由を、ユーザー向けに短くまとめる

### 9. 検証（hugo）
`cd blog && hugo --gc --minify` がエラーなく完走することを確認する。今日以前の日付なら `public/.../index.html` が生成されることも確認する。

**未来日で先積みする場合**は `hugo --gc --minify --buildFuture` で、その記事が実際にビルドできること（ショートコードや `ref` の解決を含む）を確認する。`--buildFuture` を付けない通常ビルドで**その記事が出ない**ことも、あわせて確認しておくと安心。

記事内で引用したコードや設定値は、**引用元の実ファイルと突き合わせて一致を確認する**。参考 URL は `curl -o /dev/null -s -w '%{http_code}' -L <url>` で 200 を確認する（ドキュメントの URL は移動していることがある）。

### 10. ブランチ → PR
- `main` 直コミット禁止。`feat/…` などのブランチを切る（記事なら `feat/post-<slug>` を目安に）
- 記事は blog submodule 側の変更 → **blog repo でブランチ・commit・PR**（親の submodule pointer は自動追従ワークフローに任せる）
- コミットメッセージ・PR は日本語。`--no-verify` 等のバイパス禁止

## 編集者チームレビューの回し方

**回し方そのものは `editorial-review` skill が持っている。** ここには blog 固有のことだけを書く。
レビュアーの構成・プロンプトの組み立て方・落とし穴・フォールトトレランス・止めどきの判定は
**あちらが単一の出所**なので、ここに写さない。

### 渡すもの

**`references/medium.md` にプレースホルダごとのブロックを置いてある。** そのまま渡す。

| プレースホルダ | blog での中身 |
| --- | --- |
| `{{INTRO}}` / `{{MEDIUM}}` | 媒体の説明（カタツムリワークスの技術ブログ、文体、読者） |
| `{{MEDIUM_CHECKS}}` | house style（`## まとめ` で閉じる）、コードブロックの言語指定、本文とまとめの食い違い、他の記事との矛盾 |
| `{{MEDIUM_OUTPUT}}` | タイトル案 |
| `{{CORE_MESSAGE}}` | **手順2 で決めた想定読者と読後感。** 記事ごとのネタ memo が出所 |
| `{{DOCUMENT}}` | 記事の Markdown 全文（frontmatter 含む） |

**第 1 段階の「主張 → 一次情報」の対応表は、記事ごとのネタ memo に置く。**
そのパスを `editorial-review` に渡す。

### blog 固有の注意

**実装との食い違いを拾ったら、別 PR に分ける。** `editorial-review` は
「文書の外の食い違いも拾う」と書いているが、blog では**1記事1PR を壊さない**ことを優先する。
2026-09-22 の記事では実装側の修正が3本の PR になった。

**blog は public なので、記事を読んだ人がリポジトリをそのまま見に行ける。**
記事側で慎重に限定した主張を、コード側のコメントが言い切ったまま放置していないか確認する。

**Hugo のショートコードがプロンプトの未置換チェックを壊す。** 記事本文に
`{{< ref "..." >}}` が入るため、`"{{" not in p` で見てはいけない。
`editorial-review` の「プロンプトを組み立てる」に書いてあるとおり、
**プレースホルダ名で 1 つずつ確かめる。**

## 完了時にユーザーへ返すもの
- 生成した記事のパスとタイトル
- レビュー結果の要約（どのレビュアーが動いた／スキップされたか、主な指摘と反映可否）
- **何周回したか、最後の周で事実誤りが出たかどうか**（出たなら、止めた理由も）
- ぼかしチェックの結果（落とすもの 0 件であること。警告が出たなら、その判断も）
- **`humanizer` を通した結果**（発火したパターン、太字の密度が 4〜5 に収まったか、表現の後退があれば戻したかどうか）
- hugo 検証結果、ブランチ名、PR の URL

## やらないこと
- `main` への直コミット、`--no-verify` 等のバイパス
- 機密（顧客名・個人パス・実名・認証情報）を含んだままの公開
- レビュー指摘の無批判な全反映（おかしい指摘は理由を添えて見送る）
