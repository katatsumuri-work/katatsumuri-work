# blog.snail ― 技術メモを編集者レビュー付きでブログ記事化する

`~/memo` や `~/PROJECTS` の素材から、カタツムリワークスの blog 記事の下書きを作るパイプラインです。書いた本人（この Claude）だけで完結させず、**別の LLM エージェント3者に「雑誌・書籍の編集者」として査読させてから仕上げる**のが肝です。

## 対象・前提

- 出力先ブログ: `~/PROJECTS/katatsumuri-work/blog`（Hugo。親 repo の submodule）
- 記事の置き場: `blog/content/posts/YYYY-MM-DD-{slug}.md`
- パーマリンク: `/:year/:month/:day/:slug/`。**未来日の記事は Hugo 既定で当日まで非表示**（＝日付を振れば連日公開に使える）
- 規約は親 repo の `AGENTS.md`（言語＝日本語、トーン、ブランチ戦略、コミット前チェック）に従う
- **公開は自動**。blog repo の `.github/workflows/deploy.yml` が main への push と日次（JST 09:05）で Firebase Hosting へデプロイする。マージすれば手動デプロイは不要で、未来日の記事も当日の日次ビルドで自動的に出る

作業前に必ず、既存記事を1〜2本読んでトーンを合わせること（`blog/content/posts/` の直近記事）。

## パイプライン

### 0. 入力を確定する
ユーザーの指定（日付／memo パス／repo／ネタ memo）を受け取る。**曖昧なら `AskUserQuestion` で確認**してから進む（何を元ネタにするか、公開日、`draft` の扱い＝先積みか下書きか）。1回の実行で1記事を基本とする。

### 1. 素材を読む
指定された daily_report・技術メモ・実装コードを読む。ここの目的は**「人柱ポイント（ハマった点）」を掴む**こと。記事の核をどこに置くかは次の手順で決める。

### 2. 想定読者と読後感を決める（`core-message-writing`）
書き始める前に `core-message-writing` skill を呼び、**想定読者**（誰が読むか・その人が
すでに知っていることは何か）と**読後感**（どう感じてほしいか・何をしてほしいか）を
言語化する。判断軸の中身はあちらが単一の出所なので、ここには写さない。

**ここに置く理由。** 素材を見ないと想定読者も読後感も決められないので手順1 より前には
置けない。逆に書き出し（手順6）より後ろだと、**何を削るかの判断根拠として使えない**ので
遅い。素材を読んだ直後のここが唯一の置き場所になる。

**この工程が埋める穴。** 3者の編集者レビューは事実誤りをよく拾う（09-22 の記事は
4周して計 8 件）が、**「一番言いたいことが埋もれている」は誰も指摘しなかった**。
レビュー周回のコストが実測で重いので、上流で締める。

決めた想定読者・読後感は**レビュープロンプトの `{{CORE_MESSAGE}}` に渡す**（手順8）。
宣言した狙いに照らして記事がどうかを 3者に見てもらうため。渡さないと、レビュアーは
狙いを推測しながら構成を評価することになる。

**あの skill は2段構成なので、ここで終わりではない。** 「① 書く前に決める」がこの手順、
「② 書いた後に、コアを際立たせる方向へ調整する」と最終チェックリストは**手順6 の直後**に
当てる（手順7 の `humanizer` より前）。**中身と構成を直してから表層の言い回しを直す**順に
しないと、humanizer で整えた文を後から削ることになる。

### 3. ぼかす（機密の除去・抽象化）
公開物に載せてはいけない情報を除去・抽象化する。**ここは必須工程**。
- 顧客名・取引先名 → 「あるクライアント」等に抽象化、またはプレースホルダ
- 個人名・自宅/個人の絶対パス（`/Users/...`、OneDrive の実パス等）→ プレースホルダ
- 生の認証情報・トークン・内部 URL・センシティブな数値 → 除去
- 判断に迷う値は載せない側に倒す。元ネタに顧客名リスト等があれば突き合わせて漏れを確認する。

**書いたら機械のチェックを走らせる。** 手順としての指示だけだと、そのときの注意力に
依存する。blog repo にスクリプトがある。

```sh
cd ~/PROJECTS/katatsumuri-work/blog
gcloud secrets versions access latest --secret=blog-sensitive-terms \
  --project=katatsumuri-work > /tmp/terms.txt
python3 scripts/check_sensitive.py --terms-file /tmp/terms.txt
rm -f /tmp/terms.txt
```

- **落とすもの**: 認証情報・個人の絶対パス・内部 IP・機微な固有名詞（顧客名・個人名・地名）
- **確認だけ**: 金額・住所らしき語（文脈で可否が変わるので落とさない）
- **目視用**: 外部 URL の全件。内部 URL が混ざっていないか見る

顧客名などの機微な固有名詞は **blog repo が public なので置けない**。Secret Manager の
`blog-sensitive-terms` にある。**リストを渡さないと顧客名の検査だけ行われない**ので、
上のように取り出して渡すこと（渡さない場合は警告が出るが、他の検査は走る）。

**main 宛ての PR では Cloud Build が同じチェックを自動で走らせ、落ちると merge できない**
（トリガー `blog-pr-sensitive-check`）。手元で先に通しておけば PR で驚かない。

誤検出だと判断したものは `blog/scripts/sensitive-allow.txt` に積む。ただし
**機微な語そのものをここに書いてはいけない**（public repo なので、検知したい語を
自分で公開することになる）。許可リストは `${SYNC_PAT}` のような、機微でない誤検出のためのもの。

機微な語が正当な理由で記事に必要なときは、**記事側を直すか、用語リストから外すかを
ユーザーに確認する**。2026-09-24 に実際に踏んだ判断で、結論は「GitHub のユーザー名は
公開情報なのでリストから外す」だった。

### 4. 整文（媒体トーンに整える）
既存記事に合わせる。
- 「〜です／〜ます」基調、柔らかい表現（「〜しそうです」「〜かなと思います」）を混ぜる。カタツムリらしくゆっくり
- `## 見出し` で構成し、コードは言語付きフェンスで示す
- 主張の根拠になる箇所は**公式ドキュメントの URL** を「参考:」として添える（一次情報優先）
- 最後に「## まとめ」で持ち帰りを整理する

### 5. frontmatter を生成
```yaml
---
title: '…'
slug: '…'                 # 英小文字・ハイフン
date: YYYY-MM-DDT09:00:00+09:00   # 時刻+TZ 必須。tech は 09:00 が既定
categories: ['tech']      # tech | zatsudan | yomoyamo
tags: ['…']               # 小文字スラッグ。言語/FW/ツール名
draft: false              # 先積み運用なら false + 未来日。純粋な下書きなら true
---
```

### 6. 記事を書き出す
`blog/content/posts/YYYY-MM-DD-{slug}.md` に保存する。

書き出したら `core-message-writing` の「② 書いた後に、コアを際立たせる方向へ調整する」と
**最終チェックリスト**を当てる（手順2 で決めた読後感に照らす）。とくに**見出しだけを上から
読んでストーリーが伝わるか**は、この媒体の記事で崩れやすい。

### 7. `humanizer` を通す（AI っぽさを落とす）

**編集者レビューの前**に、初稿へ `humanizer` skill を当てる。personal スコープに入っている
（`~/.claude/skills/humanizer`。実体は private-dotfiles）。

**なぜレビューの前か。** 太字の過密・「実は」・「結論を先に言うと」といった癖は、
**毎周レビューで指摘されていた**ものだった。上流で落としておけば、レビューを事実検証に
集中させられる。

**2026-10-10 に日本語で判定済み。** 26 パターンのうち 6〜7 が発火し、残りは英語固有で
空振りする（害はない）。

| 発火するもの | 空振りするもの |
|---|---|
| 太字の装飾（**最多**）／一行の締め・劇的な短文／前置き（「結論を先に言うと」「正直に言うと」）／格言調／「実は」／Not X but Y | ダッシュ／ハイフン複合語／受動態（日本語は主語省略が常態なので基準にならない）／is-has 回避／カーリー引用符／英単語リスト |

**コードブロック・コマンド出力・英語原文・コミットメッセージ・数値には手を入れない。**
これは実測で確認している。

#### 太字はこのブログの基準に寄せる

**humanizer は「装飾の太字は全部外す」方針だが、そこまでやらない。**
既存 21 記事の実測（コードフェンス除外）では、**書き進むうちに密度が上がっていた**。

| | 密度（箇所 / 1000 字） |
|---|---|
| 2026-06 の記事 3 本 | **4.2 / 4.4 / 4.6** |
| 中央値（21 本） | 7.1 |
| 2026-09-29 snail-cli | 9.5 |
| 2026-09-17 ai-driven-company-ops | 12.7 |

**初期の 4〜5 をこのブログの本来の密度と見て、そこを目標にする。** 全部外すと流し読みで
要点が拾えなくなる。

#### 通したあとに必ず確認する

**humanizer は表現の後退を生むことがある。** 実測で 3 件あった。

- 意図の言い直しが消えた
- 「絶対に」が落ちた
- **元の文に無い条件を補った**（1 箇所）

**新しい事実の捏造は無かったが、最後のものは踏み込んでいる。**
だから humanizer のあとに編集者レビューを置く順序になっている。
**通して終わりにせず、変更箇所を before / after で見る。**

#### 既存記事には通さない

公開済みを書き換えると再デプロイが走り、履歴も汚れる。**今後書く記事から適用する。**

### 8. 編集者チームレビュー（この工程が本 skill の主眼）
**検証（手順9）の前に**、書いた本人以外の LLM 3者に、雑誌・書籍の編集者として査読させる。詳細は下の「編集者チームレビューの回し方」。
- 3者の指摘を集約し、**批判的に取捨選択**して記事に反映する（全指摘を鵜呑みにしない。レビュアーが的外れなこともある）
- 反映した指摘／見送った指摘とその理由を、ユーザー向けに短くまとめる

### 9. 検証（hugo）
`cd blog && hugo --gc --minify` がエラーなく完走することを確認する。今日以前の日付なら `public/.../index.html` が生成されることも確認する。

**未来日で先積みする場合**は `hugo --gc --minify --buildFuture` で、その記事が実際にビルドできること（ショートコードや `ref` の解決を含む）を確認する。`--buildFuture` を付けない通常ビルドで**その記事が出ない**ことも、あわせて確認しておくと安心。

記事内で引用したコードや設定値は、**引用元の実ファイルと突き合わせて一致を確認する**。参考 URL は `curl -o /dev/null -s -w '%{http_code}' -L <url>` で 200 を確認する（ドキュメントの URL は移動していることがある）。

### 10. ブランチ → PR
- `main` 直コミット禁止。`feat/…` などのブランチを切る（記事なら `feat/post-<slug>` を目安に）
- 記事は blog submodule 側の変更 → **blog repo でブランチ・commit・PR**（親の submodule pointer は自動追従ワークフローに任せる）
- コミットメッセージ・PR は日本語。`--no-verify` 等のバイパス禁止

## 編集者チームレビューの回し方

レビュアーは **別の claude / codex / agy** の3者（2026-09-24 時点で手元に揃っているのはこの3つ）。プロンプトの雛形は `references/editorial-review-prompt.md`。各レビュアーに少し違う編集者ロールを割り当てて視点を散らす。

| レビュアー | 割り当てロール（{{REVIEWER_ROLE}}） | CLI |
|---|---|---|
| agy（Antigravity） | 校閲担当（事実確認・表記ゆれ・機密漏れ重視） | `agy` スキル経由 |
| claude（別インスタンス） | 書籍の編集者（構成・内容の深さ重視） | `claude -p` |
| copilot | 技術雑誌の編集者（言い回し・読みやすさ重視） | `copilot -p … --allow-all-tools`（**2026-09-24 時点で未インストール**。PATH にも global npm にも無い） |
| codex | 校閲担当（事実確認・表記ゆれ・機密漏れ重視） | `codex exec -s read-only --skip-git-repo-check …` |

3者そろえるのが基本だが、**動くものから使えばよい**。いまは `copilot` の枠を `agy` で埋めている。

**役割の実績（2026-09 の3記事）。** `claude` と `codex` が事実誤り・論理の飛躍をよく拾う。
`agy` は事実誤りをほぼ出さず、構成・文体と house style の抜け（`## まとめ` が無い等）を拾う。
**`agy` の「内容」指摘は誤読が混ざる**ので、実物に当たってから採ること。

### 手順
1. レビュアーごとに、`references/editorial-review-prompt.md` の `{{REVIEWER_ROLE}}`、`{{CORE_MESSAGE}}`（手順2 で決めた想定読者と読後感）、`{{ARTICLE}}`（記事 md 全文）を差し替えたプロンプトを、スクラッチパッドに一時ファイルとして書き出す（パス依存を避けるため本文はインラインで埋める）。

   **プロンプト生成で 2 回踏んだので注意。**

   - **テンプレートを `---` で split しない。** 記事本文の frontmatter にも `---` があるため、
     区切りを見誤って指示文が丸ごと落ちる。落ちても実行自体は成功してしまい、
     「記事だけ渡してレビューを頼んでいない」状態になる。
     `tmpl.index("あなたは技術系メディアの")` のように**指示文の開始位置から末尾まで**を取る
   - **未置換チェックに `"{{" not in p` を使わない。** 記事本文の Hugo ショートコード
     `{{< ref "..." >}}` に誤反応して落ちる。
     `"{{REVIEWER_ROLE}}" not in p and "{{ARTICLE}}" not in p` のように**プレースホルダ名で確かめる**
     （`{{CORE_MESSAGE}}` も同様に見る）

   生成したら、投げる前に**指示文が入っているか**を目視するのが確実
   （`head -3` で「あなたは技術系メディアの…」が出ればよい）。
2. 3者を**並列**で実行し、各出力を別ファイルに保存する。1つのメッセージで複数 Bash を投げるか、バックグラウンド実行を使う。

```bash
# 例（スクラッチパッドの $DIR にプロンプトを用意済みとする）
claude -p "$(cat "$DIR/prompt-claude.txt")"                     > "$DIR/out-claude.md"  2>&1
agy    -p "$(cat "$DIR/prompt-agy.txt")"                        > "$DIR/out-agy.md"     2>&1
codex  exec -s read-only --skip-git-repo-check \
       "$(cat "$DIR/prompt-codex.txt")" < /dev/null             > "$DIR/out-codex.md"   2>&1
```

`codex` の引数には注意が要る（2026-09-11 時点、codex-cli 0.153.4 で確認）。

- **`-a` / `--ask-for-approval` は廃止された。** 使うと
  `error: unexpected argument '-a' found` で即落ちる。代わりに `-s read-only`
  （サンドボックス）を指定する。レビューはテキストを返すだけなので書き込み権限は要らない
- **スクラッチパッドは git リポジトリの外**なので `--skip-git-repo-check` が要る。
  無いと `Not inside a trusted directory and --skip-git-repo-check was not specified.` で落ちる
- **`< /dev/null` で stdin を閉じる。** 閉じないと
  `Reading additional input from stdin...` のまま入力を待って止まる
- 出力にはプロンプト全文や実行ログがエコーされる。最終応答は**末尾の `codex` 行以降**にあるので、
  そこを抜き出して読む

3. 各出力を読み、指摘を統合する。**同じ指摘は束ね、対立する指摘は自分で判断**する。

   出力の形は CLI ごとに違う。`codex` は**プロンプト全文と実行ログをエコーする**ので、
   最終応答は**末尾の `codex` 行以降**を抜き出して読む。

### フォールトトレランス（重要）
- いずれかの CLI が失敗（非ゼロ終了・エラー出力）しても**全体を止めない**。そのレビュアーだけスキップし、「◯◯はスキップ（理由）」と記録して残りで続行する。
- **既知**: CLI の引数は版によって変わる。落ちたらまず `<cli> --help` で現行の引数を確認する
  （2026-09-11 に `codex` の `-a` 廃止でスキップが発生した。上の注意書きを参照）。
- 最低1者のレビューが取れれば反映に進む。**全滅した場合のみ**ユーザーに知らせて指示を仰ぐ。
- レビュアーはあくまで**別の LLM**を使うのが目的（外部の目）。この Claude 自身の自己添削で代替しない。

### レビューは1周で終わらせない（最重要）

**反映した原稿をもう一度レビューに投げること。** 2026-09 の実績では、**2周目・3周目でも毎回 `[must]` が出た**。

| 記事 | 周回 | 出た事実誤り |
|---|---|---|
| 2026-09-22（Cloud Build 移行） | 4周。3周目まで毎回 `[must]` | 計 8 件 |
| 2026-09-23（トラックボール） | 2周目でも `[must]` 7 件 | 計 9 件 |

**新規の事実誤りが出なくなった時点が止めどき**で、周回数を先に決めない。上の 2 本はどちらも、
最終周で初めて「事実誤りなし」と言われた。

踏んだパターンは次の3つ。いずれも**1周目には存在しなかった**もので、反映作業そのものが生んでいる。

- **本文を直して「まとめ」を直し忘れる。** 本文では慎重に限定したのに、箇条書きの持ち帰りに
  修正前の言い切りがそのまま残る。`## まとめ` と `## 学んだこと` は本文と別に読み直す
- **反映が新しい矛盾を作る。** 後半を書き直した結果、前半の記述と食い違う。特に**結論が変わる
  修正**のときは、前半の「見立て」が地の文のままになっていないか確認する
  （当時の見立てとして書き分けるか、直すか）
- **足した一文が前後関係を壊す。** 「あとで触れる◯◯」と書いた節が、実際には前にあった

**反映したら、前後関係の通し読みを1回入れる。** 差分だけ見ていると上の3つは見つからない。

### 記事の外の食い違いも拾う

レビューは記事だけでなく**リポジトリのコメントや実装との食い違い**を拾う。記事側で慎重に
限定した主張を、コード側のコメントが言い切ったまま放置していることがある。blog は public
なので、記事を読んだ人がそのまま見に行ける場所であることに注意。

2026-09-22 の記事では、これが3本の PR になった。

- 記事で「今回使った 2 つが古かった」と限定したのに、`cloudbuild.yaml` のコメントが
  「全体的に古い」と言い切っていた
- 記事で「Cloud Scheduler も at-least-once」と書いたのに、Terraform の変数コメントに
  「指定時刻に確実に動く」という**古い理解が化石化**していた
- 記事に「この抜粋はコピーして使うには 2 つ足りない」と正直に書いたら、**実装側に同じ穴が
  空いていた**（checksum 未検証・バージョン未固定）

**記事に「ここは弱い」と書いたなら、実装を直すかどうかまで考える。** ただし記事の PR には
混ぜず、別 PR に分ける（1記事1PR を壊さない）。

### 前提を本人に確認すると、結論が覆ることがある

2026-09-23 の記事は、**書き上げてレビューまで通したあとに結論が反転した**。「増えすぎている」
という前提でほぼ仕上げていたが、実際の使い分けを聞き取ったら誤診だった。

- 台数・構成・使い分けのような**本人しか知らない事実**は、記事の骨格を決めるなら先に聞く
- 聞かずに書けることと書けないことを切り分け、**書けない部分は推測で埋めない**
- 型番や機種が分かったら**公式ドキュメントで仕様を確認する**（このときも「1台に見えて実は
  1台で2台を掛け持ち」のような、聞き取りだけでは分からない事実が出た）

### 証明できる範囲を超えて書かない

**手元の材料から言えることと、言いたいことを混ぜない。** レビューで繰り返し出た指摘。

- 「接続先がある」と「必要である」は別。表が示すのは前者だけ
- 一例から「たいてい〜」と一般化しない。**今回はこうだった**に留める
- 未着手のことを断定で書かない（「また増えるだけです」→「また増えそうです」）
- 反証が立つなら、**反証自体を本文に書く**。潰せないなら結論を弱める。
  そのほうが記事は強くなる

### 素材そのものが消えていることがある

2026-09-23 の記事では、元ネタの一行が**ファイルから消えていた**。GTD のツールが
拾った行を `- [[リンク]]` に置換する仕様だったため。

**`git log` / `git show` で原文を復元する。** このときは復元した原文が記事の芯になった。
復元していなければ、実際より弱く不正確な記事になっていた。

### 素材が古いことがある（実績のある落とし穴）

レビューで最も価値があったのは、**記事の記述と実装の現状が食い違っている**という指摘だった。

2026-09-09 に、あるツールの紹介記事で「この機能はこれから実装する」と書いたが、実際にはすでに
実装済みだった。原因は、素材にした repo の README の一部（「現在の制約」節）が更新されずに
古いまま残っており、それを信じたこと。README の別の節には実装済みの使い方が書いてあり、
**同じファイルの中で情報が食い違っていた**。

対策として、手順1で素材を読むときは次を確認する。

- README や memo の記述を鵜呑みにせず、**`git log` で直近のコミットを見る**（実装が先行していることがある）
- 「まだ〜していない」「これから〜する」と書くときは、**実装ファイルの有無やコマンドの存在を実際に確かめる**
- 素材の repo が別セッションで並行して動いている場合は特に注意する（執筆中に実装が進むことがある）

## 完了時にユーザーへ返すもの
- 生成した記事のパスとタイトル
- レビュー結果の要約（どのレビュアーが動いた／スキップされたか、主な指摘と反映可否）
- **何周回したか、最後の周で事実誤りが出たかどうか**（出たなら、止めた理由も）
- ぼかしチェックの結果（落とすもの 0 件であること。警告が出たなら、その判断も）
- **`humanizer` を通した結果**（発火したパターン、太字の密度が 4〜5 に収まったか、表現の後退があれば戻したかどうか）
- hugo 検証結果、ブランチ名、PR の URL

## やらないこと
- `main` への直コミット、`--no-verify` 等のバイパス
- 機密（顧客名・個人パス・実名・認証情報）を含んだままの公開
- レビュー指摘の無批判な全反映（おかしい指摘は理由を添えて見送る）
